System map lelouch-harness

The Lelouch system

You talk to one agent. It interviews you until the work is pinned down, writes the decisions where other agents can read them, slices the work into dependency-ordered tickets, and dispatches supervised workers — then reports one plain outcome. This page is how all of that fits together, explained from zero.

Question one

What actually runs, and where?

Four layers. The important and non-obvious one: Lelouch and its workers are the same software reading the same contract file — they differ only by the role each is assigned at startup.

Why the contract opens with a role gate

A worker gets a git worktree of the same repo, so it loads the same CLAUDE.md. If it read the orchestrator's rule — "you do not write project code" — it would refuse the job it was dispatched for. So the file's first section asks: are you carrying an Orca taskId? Then you are a Worker; read your section and skip the rest.

Question two

What happens to one request?

Left to right. The two vertical bars are hard stops — Lelouch waits for you there, and silence is not approval.

The approval gate

The ticket breakdown goes in front of you before anything is dispatched. Not a courtesy — a hard stop. It exists because the first smoke test saw Lelouch promise to show the breakdown, then dispatch a worker first.

The design gate

Only when the project has a UI. How an app looks is never a worker's call: a design brief ships as its own PR, you take it through a design pass, and styled-UI tickets reference the result. Structural work is unaffected; a CLI skips the gate.

Question three

How does a worker know anything?

A worker never saw your conversation. It gets a task spec and a repo — so everything it needs must already be written down in files. That is what these are for.

The one thing that does not persist

A decision you have not answered yet lives only in the conversation. When the first smoke test ran out of tokens, the glossary, ADRs and backlog all survived — the open questions did not. Making a pending decision a durable backlog row is the single most valuable thing still on the list.

Question four

How does a worker reach for the right skill?

A skill is a set of instructions an agent loads on demand. There are three ways one gets invoked, and they are not equally reliable — the whole dispatch design rests on this.

Tier 1 build on this

The spec names it

Lelouch writes the skill names into the dispatched task spec. The worker reads it as its opening instruction. Reliable because nothing is left to memory.

Tier 2 ambient

The routing table

A table in CLAUDE.md, loaded at session start: when doing X, use Y. Catches a worker that drifts.

Tier 3 free, weakest

It fires on its own

Skills self-trigger from their description text. Costs nothing, fires inconsistently. This is the one people assume carries the system, and it doesn't.

Two kinds of skill

Most are prose — the instructions are the skill. A few (lavish, tasks-axi, orchestration) are CLI-backed: a thin pointer whose real guidance lives in a versioned binary, so it can never go stale. That is why you see them run npx.

Vendored twice, on purpose

18 skills ship as both a pristine vanilla copy and our patched forks. The vanilla copy is the diff baseline: when upstream changes, geass diff shows exactly what we altered, so a version bump is a real merge rather than a guess.

Question five

How does a project get all this?

One command copies the harness into the project. A project either has these files — and Lelouch runs it — or it doesn't, and you get a plain agent. Like a virtualenv: no global footprint, nothing leaking between projects. 

pip install git+https://github.com/m3dus444/lelouch-harness

cd ~/my-project
geass cast

It reads the project's own git to fill the contract in — real repo, real default branch — and checks that the external skills it depends on are actually installed, rather than letting you discover that mid-dispatch.
