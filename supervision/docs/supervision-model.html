Supervising a run from outside it

A second session watches a Lelouch run and establishes what actually happened. It never participates. This page is the observer's honest account of its own instrument: what it reads directly, what it is blind to, and what it therefore needs a human to report.

Why this is possible at all

Claude Code appends every session to a JSONL transcript as it runs. Nobody has to report anything — not the orchestrator, not its workers. The observer reads the same ground truth they wrote.

The instrument's limits

The split is not arbitrary. The transcript records what the agent did; it records nothing about what the screen showed. Everything in the right column is a consequence of that one fact.

Seen reliably — do not report these

  • Every tool call, with its full command string and result
  • Timestamps on every row → real wall-clock gaps, to the second
  • Skill invocations — which fired, in what order, in whose session
  • Subagent spawns — type and description of each
  • Token usage per session (input, output, cache)
  • Files on disk, mtimes, git state, backlog contents
  • Orca's injected nudges — they land as user-role messages
  • Which session is which — a worker's first message says so

Blind — only a human can supply these

  • The terminal UI — tab titles as displayed, spinners, layout
  • Whether a prompt actually landed in a tab, or sat waiting for Enter
  • Browser windows — Chrome launching, about:blank, profiles, debug ports
  • Subagent token usage — confirmed absent: zero sidechain rows
  • Which tab you were looking at, and what felt slow
  • Anything outside a watched project directory
A stalled dispatch is invisible: worker-start exits zero and the JSON says success. Only a person can see the tab sitting idle.

The contract-monitor skill

Packages the above so a cold session can supervise without rebuilding any of it. Deliberately lives outside geass/ — it is tooling for the supervisor, not something a project gets cast with.

live watch.py <project>

Streams one line per action — never prose. Run under the Monitor tool, persistent: true. Pass --from-now when restarting mid-run or it replays history as if it were live.

Omits orchestration check on purpose: a compliant run re-arms it constantly and silently, so streaming it floods the channel with exactly the noise the contract exists to suppress.

post-run observe.py <project>

Prints every skill invoked, per-session action counts, and the scorecard. -v for the full action list.

Answers questions a debrief otherwise can't settle — "did it really invoke to-tickets, or improvise a DAG?" is a fact in the transcript, not a judgement call.

Three things no check captures, to be read by eye: did a worker use the skills its spec named (the load-bearing mechanism of the whole design); did Lelouch narrate its machinery (§0/§7 forbid it); did the board get labelled (--display-name, --comment, terminal rename).

Judgement rules

Every one of these exists because it produced a wrong call first. They are the expensive half of the skill.

Read files, not command strings

Counting tasks-axi add calls undercounted the backlog by half. The artifact is the truth; the command that made it is a rumour.

A spec that names a command is not that command running

Specs and briefs contain the words worker-start and no-mistakes. Matching tool names anywhere in a Bash string reports dispatches that never happened — and a phantom dispatch means wrongly accusing the approval gate. Match a tool followed by a real subcommand; skip file-writing commands.

Too early is not failed — but it is not a licence either

Don't score a stage the run hasn't reached. But a Scout dispatched mid-grilling is still a dispatch, and the approval gate covers anything. This rule was originally written the other way round, excusing a real violation by reasoning from the wayfinder table's "no human needed" without reading the gate above it.

Absence of a Lavish artifact is not automatically a gate violation

The artifact is required only when the breakdown is more than two or three tickets. For a small one, look for an approval exchange instead of inferring from the file.

task-list is terminal-scoped

It reports the Run bound to your terminal. Run from an unrelated directory it returns zero. That is not evidence of anything.

Say when you are unsure, and say what would settle it

Half of what looks like a defect mid-run is a stage that hasn't happened. Name the specific event that would confirm or clear it, then wait for that event.

Reporting

During the run

Lead with what the user can act on now. Everything else waits for the debrief — the user is mid-conversation with Lelouch and every interruption costs them that thread.

At the debrief

Scorecard, then findings, then what each finding implies for the contract. A finding that does not change a rule is an anecdote.

Separate facts (from the transcript) from judgement (yours), and label a correction as a correction — being wrong loudly is cheaper than being wrong quietly.
